# NGK Sprint (analysis, cleanup, plan by tenant, groom)

Scripts do the data work (fetch, classify, group, format, update). AI only (a) reviews script output with the user, (b) decides what "old ticket that doesn't make sense" means when the user asks, and (c) writes engineering approaches in Groom. Everything is a discussion: show a report, take the user's direction, build an ops file, dry-run it, then apply on confirmation.

> **Paths** (my-jira-tracker repo, `~/Documents/git/projects/my-jira-tracker`): the scripts, libs and `config.json` live in `backend/delivery/` (`${DELIVERY_DIR}`), so the app is self-contained; this skill folder only holds this file. Everything the scripts generate (`.cache/`, `releases/`, `prs/`, `pr-analysis/`, `state/`, `flags.local.json`) goes to `backend/data/delivery/` (`${DATA_DIR}`, git-ignored); the relative data paths named below are relative to it. Credentials are read from `backend/.env` (or `JIRA_ENV_FILE`); never print them. Needs Node 18+. No npm install.
> **Read-only by default.** Only `apply.mjs --apply` changes anything (Jira or MyTracker), and only after the user confirms the dry run.

## Inputs

**Fast paths (no question, run immediately):**

- **My Tracker data (current deliverable):** daily.mjs no longer builds HTML or archived reports by default (`--html` brings the old page back). It writes `.cache/data/delivery.json` (releases for the ledger window, `toRelease` = today, `prs`); the My Tracker backend (`backend/src/routes/delivery.js`) filters it for the Release & PRs tabs (Released, To Release Today, Merged PRs today), and its "Run latest report" button re-runs `daily.mjs --no-save` (nothing is scheduled; the user runs it on demand). **Rules decide, AI only for complex PRs:** every run triages new PRs by rules (`lib/triage.mjs`): tiny ones get a rules-only entry automatically (`ai:false`, shown as "rules only"); the rest show "AI analysis pending" in the app until the user asks ("analyze today's PRs"). Then run `pr-packet.mjs --missing` (it adds related earlier PRs from the PR ledger as retrieval context: same ticket or same files), have a haiku subagent (Agent tool, `model: "haiku"`) write the JSON for light/deep packets, and run the report again. The headless `claude -p` CLI cannot do this on its own right now (its login belongs to a different organization: `claude auth login` first), so the AI step happens in a Claude session. **Tiers now:** simple (tiny, or CI/docs/tests/styles/translations only, or a version bump only: rules-only entry written automatically), standard (ordinary change: no AI unless asked), complex (reference to other PRs, sensitive path, large runtime change, >15 files, major/new/removed dependency: "AI recommended"). The app has an "Analyze with AI" button per PR (merged and open): the backend runs `scripts/analyze-pr.mjs`, which calls `claude -p --model haiku`; when the CLI is unusable it saves `pr-analysis/requests/<repo>__<n>.json` and the button shows "Queued for Claude". **"Analyze requested PRs"** = for each file in `pr-analysis/requests/`: `pr-packet.mjs --repo R --pr N` (always builds a packet), have a haiku subagent write `pr-analysis/<repo>__<n>.json` (ai:true), delete the request file, then run the report. Every run (button or script) now moves the since-last-run marker; merged PRs accumulate in the PR ledger and the Merged PRs tab filters them by merge date; open PRs are re-read each run (files/dependencies cached per PR for 6 h). Run timings are in `delivery.json` (`timing`) and shown in the app. So after a run there is nothing to open or serve: tell the user to look in My Tracker. Where the older text below mentions daily.html or serve.mjs, it applies only with `--html`.
- **Daily summary** ("daily", "summary", "what's up today", `/ngk-sprint daily`): run `node ${DELIVERY_DIR}/scripts/daily.mjs` in the user's terminal (needs their Jira creds and gh login; use run_in_terminal, reuse/close finished tabs). It writes `.cache/daily.html` (the main deliverable, self-contained), `.cache/daily.md` and `.cache/daily.json`, and prints a 5-line run summary. Sections: (1) **Completed releases**: Release tickets dated the previous business day (date from the ticket title, else due date, NOT the fix version; may or may not be released), with components (title + Jira Components field) and tickets + software versions parsed from the description table; (2) **Needs release today**: active-sprint tickets (FE component) whose fix version date is today and that are not ready, with the open release ticket if any ("none yet" if not created); (3) **Merged PRs by repo, strictly what merged since the last run** (the window is saved in `state/run.json`; each normal run starts where the previous one ended; `--rerender` re-draws the same window without moving it; `--since "YYYY-MM-DD HH:MM"` starts elsewhere; `--no-save` leaves the marker; `--date` is a historical view). Each PR shows ticket, two lines on what was built, its **change understanding** and a "Depends on" column. **Standard daily routine (cost-tiered):** (1) `usage` baseline: call `get_usage` and note plan % (5-hour, weekly) and context tokens; (2) run daily.mjs; (3) run `pr-packet.mjs --missing`, which triages each PR into **skip** (tiny translation/style/asset/test change: a rules-only entry is written, no AI), **light** (8 KB packet) or **deep** (version bump, cross-repo reference, payment/auth path, or large: 16 KB packet) and prints the plan; (4) read light packets with a **cheaper-model subagent** (Agent tool, `model: "haiku"`, or "sonnet" if haiku summaries look thin), giving it the packet paths and the JSON schema from PR analysis, and have it write the analysis files; read deep packets yourself; (5) `daily.mjs --rerender`; (6) `get_usage` again and append a row to `state/usage.md` (date, PRs by tier, models used, plan % before/after, context tokens before/after). Never analyze more than the triage plan says unless the user asks. Every PR is also recorded in the PR ledger (`prs/`) and **Dependencies and cross-component links**: found by rules, never guessed (`lib/prdeps.mjs`): version bumps in pom.xml/package.json patches, PRs referenced in other repos (with their state), the same ticket merged in several repos (repo to component map is `repoComponent` in config.json), Jira "blocked by" links, and the components the release ticket itself declares for the ticket (read from the release ledger; flags components the PRs do not cover, e.g. DB or PROD/config.json); Every section and card is collapsible, and repos with no merged PRs are not shown. Open PRs and flagged tickets are intentionally not in the report. Repos come from `config.json`. Options: `--date YYYY-MM-DD`, `--component any`. After the run, show the user the key tables (read daily.md) and open the report **through a local server, not as a file**: start `node ${DELIVERY_DIR}/scripts/serve.mjs` in a terminal tab (serves `.cache` on 127.0.0.1:8791; skip if already running) and open `http://127.0.0.1:8791/daily.html` with the browser tool. Preview panes show file:// pages as static snapshots where scripts do not run, so Expand/Collapse all and the filters only work from the localhost URL (or a normal browser). The page has a global search plus a dedicated Component/version filter. Do not add analysis unless asked.
- **What changed in the last few days** ("what merged this week", "what changed for BK-DE since Monday", "follow NGK-102178"): `node ${DELIVERY_DIR}/scripts/changes.mjs --since 3d [--tenant X] [--repo X] [--ticket NGK-1] [--text word] [--what all|prs|releases] [--format table|full|json]`. It reads the two local ledgers only (no network): `prs/ledger.json` (every merged PR the daily runs saw, with ticket, tenants, dependency facts and change understanding; tenant is inferred from the title or ticket summary when the Jira Client is empty) and `releases/ledger.json`. Report both sections in tables, say how many PRs have a change understanding, and mention the coverage note it prints if the span starts before the ledger does (catch up with `daily.mjs --since DATE --no-save`, then `--rerender`). Per-PR markdown is in `prs/md/`, the index in `prs/PRS.md`; for the RAG data feed pass `--rag-dir <datafeeds folder>` to daily.mjs (copies `ngk-prs` and `ngk-releases` there) once the user has given the path.
- **PR analysis** ("analyze kiosk-ui#9230", "analyze today's PRs", "go deeper on the BK-DE PRs"): the daily report has an Analysis/Details button per merged PR that opens a modal (facts by rules, plus my reading if an analysis exists). To write analyses: (1) in the user's terminal run `node ${DELIVERY_DIR}/scripts/pr-packet.mjs --repo REPO --pr N[,N]` (or `--missing` for every merged PR in the last daily run without an analysis); it writes `.cache/pr-packets/<repo>__<n>.md` (ticket text, PR text, commits, changed files by kind, dependency facts, trimmed patches). (2) Read each packet and write `${DATA_DIR}/pr-analysis/<repo>__<n>.json` with: `repo, number, ticket, generatedAt, basis, risk (low|medium|high), summary` (2-3 sentences: what it does), `how` (bullets on the implementation), `dependencies` (your reading beyond the rule facts), `confirm` (specific things the user should verify: null/default handling, deploy order, consumers of a changed API, config or schema prerequisites, unchecked checklist items, anything in the ticket the diff does not do). Base every statement on the packet; never claim something the diff or ticket does not show, and mark uncertainty in `confirm`. (3) Re-run daily.mjs; analyses are cached per PR (merged PRs do not change), so each PR is analyzed once. Cost control: triage tiers and packet sizes live in `config.json` "analysis"; `--deep` / `--light` on pr-packet.mjs override the tier for named PRs. Skip-tier entries carry `ai: false` and the modal says "Not AI-reviewed". To go deeper on one, run `pr-packet.mjs --repo R --pr N --deep` after deleting its analysis file. The modal labels this section "AI-assisted reading, verify".
- **Release questions** ("what was released for BK-ES last week", "which release carried NGK-102738", "FE versions shipped this month"): answer with the query script, which only reads the ledger (no Jira, works anywhere): `node ${DELIVERY_DIR}/scripts/releases.mjs --tenant BK-ES --since 7d`. Filters: `--tenant A,B`, `--since 7d|2w|1m|YYYY-MM-DD` (default 7d), `--until`, `--on DATE`, `--status released|open`, `--component FE`, `--ticket NGK-1`, `--version FE`, `--text word`; output `--format table|full|json|html`, `--group tenant|date` (`--format html` writes `.cache/releases.html`, the same table with the search and component filters; run it in the user's terminal and open `http://127.0.0.1:8791/releases.html` via serve.mjs, e.g. for "BK-US last 10 days releases" run `releases.mjs --tenant BK-US --since 10d --format html`); `--stats` shows what the ledger covers. Translate the user's question into these flags, run it, and report the result in a table. "Released" = the release ticket's Jira status is done (it can lag reality; say so). If the script warns the ledger does not reach back far enough, tell the user and have them run `node ${DELIVERY_DIR}/scripts/releases-sync.mjs --days N` (needs their Jira creds, so use the terminal tool). The ledger lives in `${DATA_DIR}/releases/` (ledger.json, one `md/<KEY>.md` per release, `RELEASES.md` index). To make the markdown queryable through the RAG data feed pass `--rag-dir <datafeeds folder>` to releases-sync or daily (copies into `<dir>/ngk-releases`), only once the user has given the folder path.
- **Flag / unflag** ("flag NGK-123", "unflag 123"): `node ${DELIVERY_DIR}/scripts/flag.mjs add|remove KEYS` (or `list`). Flags are the MyTracker stars (backend :3050); if it is down they go to `flags.local.json` and the script says so. Confirm the keys back to the user in one line. Flags are no longer shown in the daily report; show flagged-ticket status only when the user asks for it.

**Otherwise, first question (AskUserQuestion), before any script runs:** "What do you want to do?"

- **Data cleanup**: no-client suggestions, old tickets to close with a note, no UAT/no due, past due.
- **Plan by tenant**: grouped delivery view; then move dates, change fields, flag important.
- **Groom a ticket**: deep engineering approach for one ticket, posted to Jira on approval.
- **My open tickets**: my own risk-sorted list (OVERDUE / URGENT / SOON / NO DATE).

If the user already named the track in the same message (e.g. `/ngk-sprint cleanup`), skip the question and go on. Never start loading or reporting without knowing the track.

**Defaults (do NOT ask scope questions; the user wants few questions):**

- Sprint: the **current active sprint(s)**, name prefix **`NGK Sprint`**.
- Tickets: **active only** (not done).
- Excluded ticket types (always): **Release, Content Change Request, Coupon Change Request, Sub-task** (`--exclude-types none` keeps all).
- Component: **FE** always (`--component FE` is the script default).
- FE team-member filter: off (only when the user asks: `--fe`).
- Only change a default when the user's prompt says so: "future sprint" / "wide" -> `--include-future`; "future only" -> `--future-only`; a specific sprint/JQL/tenant -> `--jql`; "all components" -> `--component any`; "include done" -> `--include-done`; "my tickets" -> `mine.mjs`.
- **Groom** needs a ticket key; ask only if missing.

## Steps

0. **Ask the track** (above) only if not already named. No other questions; apply the defaults and state them in one line.
1. **Load** the scope the user chose:
   - Current sprint: `node ${DELIVERY_DIR}/scripts/snapshot.mjs [--include-future | --future-only] [--component any] [--fe] [--include-done]`
   - My open tickets: `node ${DELIVERY_DIR}/scripts/mine.mjs [--sprint-only] [--save]`. Prints a risk-sorted table. Add `--save` when cleanup/plan should run on just my tickets.
   - Specific scope: `snapshot.mjs --jql "..."` or `--filter <id>`.
   Report the counts the script prints (loaded -> after sprint filter -> after FE filter) and the sprint names found, so the user can see exactly what is in scope.
2. **Run the chosen track** (below). Open with a 3-5 line headline from the script output. Do not run the other tracks unless asked. After the track, ask what next (another track, update, or done). "Daily Jira" with no track = ask the question in step 0.
3. **Data cleanup**: `node ${DELIVERY_DIR}/scripts/cleanup.mjs [--stale-days 60]`. Four sections:
   - No client + suggested client (rule-based, with confidence and reason). User says "update 1,3,5" or "update all high".
   - Old / stale candidates. For ones the user picks, draft a short closing note (use the facts from the table; do not invent reasons) and close.
   - No UAT and no Due. Ask the user per tenant what to do (date, close, move out of sprint); never guess dates.
   - Past due. Same: per-tenant direction.
4. **Plan by tenant**: `node ${DELIVERY_DIR}/scripts/plan.mjs [--tenant BK-DE]`. Grouped by client with Ticket, Description, Component, UAT, Release, Due, Status, ★. User then asks to move dates, change fields, or flag important.
5. **Update**: translate the user's decisions into an ops file `.cache/ops-<date>.json` (format in the header of `scripts/apply.mjs`), run `node ${DELIVERY_DIR}/scripts/apply.mjs <ops.json>` (dry run), show the output, and ask "apply?". On yes, rerun with `--apply`. Then re-run `snapshot.mjs` so the next report reflects reality.
   - Supported: client, due, UAT, labels, any raw field, comment, close (transition + resolution), ★ important flag (MyTracker, needs backend on :3050).
6. **Groom `<KEY>`**: `node ${DELIVERY_DIR}/scripts/groom-context.mjs <KEY>` gathers fields, description, comments, links, subtasks, and recent same-client tickets. Then read the relevant repo code (components point to the repo; use datafeed-rag or the `foreman` / `plan-dev-task` skills for routing), write an engineering approach (scope, files, risks, test plan, flags, open questions), show it to the user, and on approval post it with a `comment` op via `apply.mjs`. Per Tillster rules: new behavior behind a LaunchDarkly flag with per-brand targeting, no hard cloud dependency on kiosk paths.

## Output

- Markdown tables in the chat (scripts print them; do not retype them).
- Dry-run diff before any write; a one-line result per ticket after.

## Notes / gotchas

- **Sprint scope**: `openSprints()` in JQL, then client-side name-prefix filter (JQL cannot do "starts with" on sprint names).
- **Ready for QA counts as done** for risk/reporting (matches `dailyBriefingService.js`).
- Field IDs: Client `customfield_16047`, UAT `customfield_16050`, Sprint `customfield_10007`. Client is a multi-select; `set.client` takes a string or array.
- The first Jira search page is sometimes empty (known flakiness); the helper retries.
- Client suggestions are heuristics (title match, learned prefixes like RCUSSD→RC-US, parent). Always show confidence; the user confirms.
- Closing transitions differ per workflow; `apply.mjs` fails with the list of available transitions rather than guessing.
- Comments/closure notes are written to external-facing Jira tickets: keep them factual, and have the user review the text in the dry run.
- Never put card data, secrets, or guest PII in comments.
